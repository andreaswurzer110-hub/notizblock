## Was das ist

Plattformübergreifende Notizblock-App in **Flutter (Dart)**.
Eine Codebasis für **Android, Windows und Linux**.

Kernfunktionen:
- Notiz-Typen: Text (kein Markdown/keine Bilder), Autopool-Tabelle (Geräteliste), Einkaufsliste (Artikel mit Menge + Abhaken)
- Notizen in Ordner sortieren (Seitenmenü/Drawer-Filter); optionales Android-Ordner-Widget öffnet die App direkt im Ordner
- Post-it-Style Widgets: auf Android Homescreen-Widgets (Notiz + Ordner), auf Windows „Sticky Notes"-Fenster
- Schlichtes Design, abgerundete Ecken
- Mehrsprachig, **Deutsch als Standard**, Sprache umschaltbar
- Google-Drive-Backup/Sync für plattformübergreifenden Abgleich

## Tech-Stack

- **State:** provider
- **Lokale DB:** sqflite (+ sqflite_common_ffi für Windows/Linux), path, path_provider
- **Google Drive:** googleapis, googleapis_auth, google_sign_in, http
- **Widgets (Android):** home_widget
- **Desktop-Fenster:** window_manager (Position/Größe der Sticky-Notes), url_launcher (OAuth-Browser)
- **UI:** flutter_staggered_grid_view, Material Design
- **Sonstiges:** uuid, intl, shared_preferences, flutter_localizations

## Architektur

```
lib/
  models/      # Note-Datenklasse
  providers/   # State (provider)
  screens/     # Bildschirme/Seiten
  widgets/     # wiederverwendbare UI-Komponenten
  services/    # database_service.dart, google_drive_service.dart, …
  l10n/        # Lokalisierung (de = Standard)
```

**Note-Model:** id (uuid), title, content, createdAt, modifiedAt, color (Default `#FFFDE7`), isPinned, isArchived, `type` (`text`/`autopool`/`shopping`), `autopoolData` (generisches Struktur-JSON, von autopool UND shopping genutzt), `folder` (Ordnername, leer = keiner; wird mit der Notiz synchronisiert).
**DatabaseService:** Singleton; auf Windows/Linux `sqfliteFfiInit()` + `databaseFactoryFfi`; Tabelle `notes` mit Indizes auf `modifiedAt` und `isPinned`. DB-Version aktuell **5** → Schema-Änderungen über `_onUpgrade` migrieren, nicht hart neu anlegen (v2 = `deletions`-Tabelle; v3 = Spalten `type`+`autopoolData`; v4 = Spalte `folder`; v5 = `sync_base`-Tabelle für die Konflikt-Erkennung). **DB-Speicherort:** Desktop (Windows/Linux) = `getApplicationSupportDirectory()` (`%APPDATA%\com.example\notizblock\` bzw. `~/.local/share/…`, neben `sticky_state/`); Android/iOS = `getApplicationDocumentsDirectory()` (dort liest das Home-Widget `notes.json`). Früher lag die DB auf Desktop im Dokumente-Ordner → einmalige Migration via `_migrateDbFromDocuments` (kopiert DB + WAL/SHM/Journal, falls am neuen Ort noch keine existiert).

## Bekannte Stolpersteine / offene Punkte

- **home_widget:** mind. `^0.7.0` – ältere Versionen ziehen das gelöschte Android-**v1-Embedding** und der Build scheitert. Bei „deleted Android v1 embedding"-Fehler zuerst hier ansetzen.
- **sqlite3.dll auf Windows/Linux:** `sqflite_common_ffi` lädt die native `sqlite3`-Lib zur Laufzeit, bündelt sie aber nicht selbst. Ohne `sqlite3_flutter_libs` als Dependency wirft `openDatabase()` „Failed to load dynamic library 'sqlite3.dll'" → quasi die ganze Desktop-App tot. `sqlite3_flutter_libs` ist daher Pflicht (steht in `pubspec.yaml`).
- **DB-Lock prozessübergreifend – `onConfigure` mit `busy_timeout` + WAL ist PFLICHT (`database_service.dart`):** Auf Desktop öffnen Hauptapp UND jedes Sticky-Note-Fenster (eigene Prozesse) dieselbe `notizblock.db`; auf Android öffnet zusätzlich das Background-Sync-Isolate eine eigene Verbindung. Ohne `busy_timeout` liefert SQLite bei Lock-Kollision SOFORT „database is locked" (SQLITE_BUSY, Code 5) statt zu warten; im Default-Journal-Modus (Rollback) blockiert außerdem jeder Schreiber ALLE Leser. War real ein Bug: Sync hängt bei einer Notiz, paralleler Sync im Hauptmenü scheitert mit „database is locked" schon beim `PRAGMA user_version` (das läuft beim Öffnen). Fix: `openDatabase(..., onConfigure: _onConfigure)` setzt pro Verbindung `PRAGMA busy_timeout=5000` (warten statt scheitern) **dann** `PRAGMA journal_mode=WAL` (nebenläufige Leser/Schreiber, prozessübergreifend). Reihenfolge wichtig (busy_timeout zuerst, damit der WAL-Wechsel selbst warten kann). `onConfigure` NICHT entfernen; `busy_timeout` muss pro Verbindung gesetzt werden (nicht persistent), WAL bleibt in der Datei. **WICHTIG – beide PRAGMAs über `db.rawQuery(...)`, NICHT `db.execute(...)`:** Beide liefern einen Wert zurück (busy_timeout den gesetzten Wert, journal_mode den neuen Modus). Androids SQLite weist sie über `execute()`/`execSQL()` ab („Queries can be performed using SQLiteDatabase query or rawQuery methods only.") → die DB ließ sich auf Android GAR NICHT mehr öffnen: leere Notizliste, jeder Sync scheiterte schon beim Öffnen (war real ein Bug 1.25.7.1–1.25.9.1; der Fix war nur auf Windows-ffi getestet, das `execute` für diese PRAGMAs schluckt). `rawQuery` führt das Statement genauso aus (setzt den Wert) und funktioniert auf Android **und** Desktop-ffi. NICHT auf `execute` zurückändern.
- **Sync-Konflikt = nur bei ECHTEM Verlust melden (`google_drive_service.isSkippedChange`):** Ein Konflikt liegt NUR vor, wenn beim Zusammenführen eine Änderung übersprungen/überschrieben wird. Die alte Prüfung „lokal seit dem letzten Sync geändert UND Remote-Datei neu in der Liste" ist dafür untauglich: sie trifft auch auf die EIGENE gerade hochgeladene Datei zu (z.B. wenn Hauptfenster und Sticky-Fenster parallel syncen und `last_remote_sync_time` dabei zurückspringt) → es kam dauernd „Konflikt", obwohl alle Änderungen vom selben Gerät stammten (war real ein Bug bis 1.30.x). Grundlage ist jetzt der **Basis-Stand** pro Notiz (Tabelle `sync_base`, `DatabaseService.get/setSyncBase`): das `modifiedAt` der Fassung, die dieses Gerät zuletzt mit Drive ausgetauscht hat. Zusätzlich schreibt der Push das Feld `basedOn` in `notes/<id>.json` – nur damit erkennt die GEGENSEITE, dass ihr hochgeladener Stand übersprungen wurde. Regeln: Remote == Basis → nie ein Konflikt; beide Seiten seit der Basis geändert → Konflikt; nur remote geändert → Konflikt nur, wenn `basedOn` ÄLTER als die eigene Basis ist. Unbekannte Basis (`null`, z.B. direkt nach dem Update oder wenn eine ältere App-Version zuletzt geschrieben hat) → **nicht** warnen; die Basis setzt sich beim nächsten Push/Pull der Notiz selbst. Abgesichert durch `test/sync_conflict_test.dart` – bei Änderungen an der Sync-Logik diese Fälle prüfen. **Basis bei JEDEM Drive-Austausch mitschreiben** (Pull, Push, `createBackup`, `restoreBackup`, `restoreDeletedNoteRemote`) – ein vergessener Pfad bringt die Fehlalarme zurück.
- **Konflikt-Hinweis gehört an die Notiz, nicht ins Hauptmenü:** In der Notizliste war er wirkungslos (man kann dort nichts damit anfangen und klickt ihn weg). Er erscheint über `widgets/conflict_banner.dart` in den drei Editoren (Text/Autopool/Einkaufsliste) und im Desktop-Sticky-Fenster. Das Banner liest den `ConflictStore` **selbst** (3-s-Takt) statt über den `NotesProvider` – das Sticky-Fenster ist ein eigener Prozess OHNE Provider, und dort syncen Haupt-App und Fenster unabhängig. Aus demselben Grund kommt `onShowVersions` vom Aufrufer: im Sticky-Fenster muss `showVersionHistory` mit eigenem `onRestore` laufen.
- **Sticky-Fenster darf Fremdänderungen NICHT mit altem Text überschreiben (`sticky_note_screen._checkExternalUpdate`, war real ein Bug bis 1.31.3):** Der Übernahme-Schutz hing an `FocusNode.hasFocus`. Der Fokus bleibt in Flutter aber gesetzt, auch wenn das Fenster längst im Hintergrund liegt – ein Sticky-Fenster, in das irgendwann einmal geklickt wurde, meldet dauerhaft `hasFocus == true`. Folge: die eintreffende Fassung wurde NICHT ins Textfeld übernommen, `_note` aber trotzdem darauf gesetzt → der nächste `_saveNote()` verglich Feldinhalt (alt) gegen `_note.content` (neu), sah einen Unterschied und schrieb den ALTEN Stand mit frischem `modifiedAt` zurück. Der PC überschrieb damit im 15-s-Takt (`_runStickyAutoSync` speichert vor jedem Sync) Änderungen anderer Geräte; auf dem Handy kam zu Recht Konflikt um Konflikt. Maßgeblich ist jetzt `_isTypingNow` (letzte echte Eingabe < 5 s, gesetzt in `_onTextChanged`/`_onAutopoolChanged`/`_onShoppingChanged`), NICHT der Fokus. **Nicht auf `hasFocus` zurückändern** – und beim Ändern dieser Stelle daran denken, dass `_saveNote` seine Änderungserkennung gegen `_note` fährt: wer `_note` aktualisiert, ohne die Anzeige nachzuziehen, erzeugt genau diesen Rückschreib-Fehler.
- **Autostart-Verknüpfung zeigte auf die Build-Exe → zweites Taskleisten-Symbol (war real ein Bug bis 1.31.6, Ursache 2026-08-10 gefunden):** `_enableWindows()` schreibt die Verknüpfung immer auf `Platform.resolvedExecutable`. Ein einziger Start aus dem Build-Ordner genügt, und die Startup-.lnk zeigt dauerhaft dorthin (auf Andis PC seit 02.08.2026, Ziel `…\build\windows\x64\runner\Release\notizblock.exe --widgets`). Ab dann startet **jede Anmeldung** die falsche Exe: die hat KEINE Paket-Identität, bekommt vom System KEINE AppUserModelID und gruppiert deshalb in einem eigenen Taskleisten-Symbol statt beim angehefteten Paket-Eintrag – dazu arbeiten zwei Installationen auf derselben DB. Das Einmal-Flag `autostart_shortcut_refresh_v5` half nicht, weil längst gesetzt. Seit 1.31.7 prüft `_repairForeignShortcut()` bei JEDEM Start: läuft die Paket-Variante und hat die .lnk ein **Datei-Ziel**, stammt sie aus einer fremden Installation und wird neu geschrieben (korrekt ist für das Paket eine Shell-Item-Verknüpfung OHNE Datei-Ziel). **Diagnose-Werkzeuge:** `Get-Process notizblock | Select Id,MainWindowTitle,Path` (muss überall `WindowsApps` zeigen) und `GetApplicationUserModelId`/`GetPackageFamilyName` per P/Invoke pro PID – leer bzw. „keine" heißt: falsche Exe. Nicht am Fenster messen, `SHGetPropertyStoreForWindow` liefert für diese App immer eine leere explizite AUMID.
- **Auf Andis PC NIE die Build-Exe starten, immer das Paket:** `build\windows\x64\runner\Release\notizblock.exe` und die installierte `C:\Program Files\WindowsApps\AW.NotizblockAW_<ver>_x64__…\notizblock.exe` sind zwei verschiedene Programmdateien → Windows macht daraus **zwei Taskleisten-Symbole** (Hauptfenster beim einen, Widgets beim anderen), und beide Instanzen arbeiten auf derselben DB. Genau so passiert 2026-08-10: für einen Screenshot wurde die Build-Exe mit `--show-main` gestartet, die ihre Sticky-Kinder über `Process.start(Platform.resolvedExecutable, …)` ebenfalls aus dem Build-Ordner öffnete. Start immer über `shell:AppsFolder\AW.NotizblockAW_3sm2ddafgswd6!notizblock`. Prüfen lässt sich das mit `Get-Process notizblock | Select Id,MainWindowTitle,Path` – alle Zeilen müssen auf `WindowsApps` zeigen.
- **Windows-Build braucht VS-C++-Workload:** `flutter doctor` muss „Desktop development with C++" grün zeigen (MSVC, C++ CMake tools, Windows SDK). Fehlt die Workload → „Unable to find suitable Visual Studio toolchain". Im Visual-Studio-Installer nachinstallieren.
- **Linux (Zorin OS):** Plattform via `flutter create --platforms=linux .` ergänzt (`linux/`-Runner, Binary `notizblock`, App-ID `at.aw.notizblock`). **Build nur auf Linux-Host** (nicht von Windows aus cross-baubar). Build-Deps auf Zorin/Ubuntu: `clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev libstdc++-12-dev`. Bauen + installieren über `scripts/install_linux.sh` (legt Bundle nach `~/.local/opt/notizblock`, Icon nach hicolor, `.desktop`-Launcher). Plattform-Anpassungen: Autostart = `.desktop` in `~/.config/autostart/` (`AutostartService`, Linux-Zweig); Sticky-Prozess-Check via `/proc/<pid>` + Schließen via `kill` (statt `tasklist`/`taskkill`); UI-Gates auf `_isDesktop` statt `Platform.isWindows`. Fenster-Icon: `gtk_window_set_icon_name(window,"notizblock")` in `my_application.cc` → löst sich nach Icon-Install auf. **Wayland-Caveat:** absolute Fensterposition (`window_manager` setPosition/getBounds für Sticky-Bounds + `--pos`) funktioniert nur unter **X11** zuverlässig; unter Wayland ignoriert der Compositor App-Positionen → ggf. Xorg-Session wählen. **Sticky-Bounds speichern (alle Desktops, v.a. Linux):** Die Fenster-Lage wird NICHT nur über die `window_manager`-Events (`onWindowMoved/Resized/Close`) gesichert – die feuern auf Linux unzuverlässig, und beim Reboot wird der Sticky-Prozess hart beendet (kein sauberes Close) → letzte Größe ginge verloren. Deshalb pollt `StickyNoteScreen._boundsSaveTimer` alle 2 s `getBounds()` und schreibt bei Änderung (`_saveBounds` mit Diff-Check). Unter **nativem** Wayland bleibt die **Position** verloren (`gtk_window_get_position`→0,0, `gtk_window_move` ignoriert). **Lösung: der Linux-Runner (`linux/runner/main.cc`) erzwingt standardmäßig `setenv("GDK_BACKEND","x11",0)`** → die App läuft über **XWayland**, dort funktionieren get/setPosition wieder, also merkt sie sich Position+Größe auch in einer Wayland-Sitzung (wie Windows). Gilt für jeden Prozess (Haupt+Stickys, gleiche Binary), überschreibbar mit `GDK_BACKEND=wayland ./notizblock`. Trade-off XWayland: fraktionale Skalierung evtl. leicht unscharf. (Reine Wayland-Sessions ohne XWayland gibt's auf GNOME praktisch nicht.) Eine echte Xorg-Sitzung tut dasselbe ganz ohne den Trick. **Taskleisten-Gruppierung:** Die `.desktop`-Datei MUSS nach der GTK `application-id` (`at.aw.notizblock`) benannt sein (`at.aw.notizblock.desktop`), NICHT `notizblock.desktop`. Bei Namens-Mismatch findet GNOME keine Zuordnung → jedes Fenster wird einzeln angezeigt (war real ein Bug). `StartupWMClass=at.aw.notizblock` zusätzlich als X11-Fallback. - **google_sign_in hat keine Desktop-Impl:** `signInSilently()`/`signIn()` daher nur auf Android/iOS aufrufen (in `main.dart` per `Platform.is…` gekapselt), sonst Exception beim Start.
- **WICHTIG – Android-Access-Token lebt nur ~1 h (Auth-Header NIE einfrieren):** `GoogleAuthClient` muss die Header **pro Request** frisch aus `_googleSignIn.currentUser?.authHeaders` holen, NICHT einmal beim Login einen Header-Schnappschuss speichern. Sonst liefert der erste Drive-Request nach ~1 h **401** → `_handleAuthFailure()` loggt hart aus → Status springt auf „abgemeldet" (durchgestrichenes `sync_disabled`-Icon). War real ein Bug: Nutzer wurde am Handy nach ~1 h Vordergrund-Nutzung und „fast bei jedem Netzwechsel" ausgeloggt (Netzwechsel = nur der Auslöser, weil resume einen Sync feuert; das abgelaufene Token war die Ursache). Erst durch den sichtbaren Login-Status (v1.20.0) aufgefallen, vorher heilte der nächste App-Start still. **Hat NICHTS mit dem OAuth-Consent-Screen „Testing→Produktion" zu tun** – das betrifft nur das Desktop-7-Tage-**Refresh**-Token, nicht das Android-1-h-**Access**-Token. Fix: (1) Header pro Request frisch; (2) bei 401 mobil `clearAuthCache()` + Token still erneuern und Operation **einmal** neu versuchen (`_refreshMobileToken` + `allowAuthRetry`-Param in `_doSynchronize`/`createBackup`/`restoreBackup`), erst bei erneutem Fehlschlag echtes `_handleAuthFailure`; (3) Sicherheitsnetz in `NotesProvider._runAutoSync`: bei `!isSignedIn` vor dem Sync still `signInSilently()`. Desktop unberührt (`autoRefreshingClient` refresht selbst; dortiges 401/invalid_grant = totes Refresh-Token = echtes Neu-Anmelden nötig).
- **Google-Drive-OAuth – Desktop läuft & getestet, Android offen.** Auth-Schicht ist plattformgeteilt: Desktop (Windows/Linux/macOS) nutzt `googleapis_auth` `clientViaUserConsent` (Loopback-Server + Browser via `url_launcher`), Token werden in `shared_preferences` (`drive_desktop_credentials`) persistiert → stiller Re-Login. Mobil (Android/iOS) nutzt weiter `google_sign_in`. Desktop-`client_id`/`client_secret` (Typ „Desktop app") stehen in `lib/services/google_drive_config.dart` (enthält echte Secrets → bei Git unbedingt gitignoren). Cloud-Projekt-ID `445597891658`, Drive API aktiviert, Test-User eingetragen. Sync = last-write-wins über `modifiedAt` (so gewollt). **Offen für Android:** OAuth-Client Typ „Android" mit Paketname + SHA-1 in der Cloud Console anlegen, dann auf echtem Gerät testen.
- **Android-Homescreen-Widget (`home_widget` + `NoteWidgetProvider.kt`):** Liest die aktuelle Notiz aus `app_flutter/notes.json` (von `DatabaseService._updateWidgetJsonFile` geschrieben). Layout `note_widget.xml`: Content-`maxLines` hoch (1000) → zeigt beim Vergrößern mehr. Notizfarbe wird im Provider auf den Hintergrund übernommen (API≥31 `setBackgroundTintList` → Ecken bleiben rund, sonst `setBackgroundColor`), Textfarbe nach Luminanz. **WICHTIG:** Update-Broadcast muss voll qualifiziert sein (`qualifiedAndroidName='com.example.notizblock.NoteWidgetProvider'` in `WidgetService.updateWidget`), weil die Provider-Klasse im Namespace `com.example.notizblock` liegt, die applicationId aber `at.aw.notizblock` ist – sonst trifft der Refresh die Klasse nicht. **WICHTIG – Broadcast zentral in `_updateWidgetJsonFile`:** Nach dem Schreiben von `notes.json` ruft `DatabaseService._updateWidgetJsonFile` direkt `WidgetService.instance.updateWidget()` auf. Das ist der gemeinsame Chokepoint ALLER DB-Schreibwege (auch Delta-Sync/`insertOrUpdateNotes`). Vorher feuerte der Broadcast nur über `NotesProvider` bei lokalen Aktionen → Remote-Sync-Änderungen aktualisierten das Widget erst nach dem 1-h-`updatePeriodMillis`. Den Broadcast also NICHT aus `_updateWidgetJsonFile` entfernen.
- **Editor speichert beim Tippen (entprellt 1 s) bei bestehenden Notizen** (`_saveDebounce` in `NoteEditorScreen`), damit der Auto-Sync zeitnah hochlädt statt erst beim Schließen. Neue Notizen weiterhin erst beim Schließen (sonst Duplikate, da `widget.note` null bleibt). Lifecycle: Sync auch bei `paused` (App geht in den Hintergrund) – nicht nur `resumed` –, damit Änderungen vor dem Einfrieren der Timer noch hochgehen.
- **Cross-Device-Pull (alle Plattformen):** `NotesProvider._remotePullTimer` zieht alle 15 s von Drive (`_runAutoSync`). Läuft nur im Vordergrund – auf Android pausieren Timer im Hintergrund (kein Akkuverbrauch). Zusätzlich: einmaliger Sync ~2 s nach Start **und** Sofort-Sync bei Rückkehr in den Vordergrund (`WidgetsBindingObserver.didChangeAppLifecycleState` → resumed). Alles nur bei aktivem Auto-Sync + Anmeldung. So fließt es in beide Richtungen (PC↔Handy).
- **Hintergrund-Sync Android (`workmanager`, `BackgroundSyncService`):** Da Vordergrund-Timer im Hintergrund pausieren, zieht zusätzlich ein **WorkManager-Periodic-Job** alle **1 h** auch bei geschlossener App von Drive – so aktualisiert sich das Homescreen-Widget mit Fremdgeräte-Änderungen ohne App-Öffnen. Top-Level `backgroundSyncCallbackDispatcher` (`@pragma('vm:entry-point')`, eigenes Isolate): `ensureInitialized` → Auto-Sync-Pref prüfen → `signInSilently()` → `synchronize()`; der Widget-Broadcast läuft dann über `DatabaseService._updateWidgetJsonFile`. Job-Lifecycle an den Auto-Sync-Schalter gekoppelt (`SettingsProvider.setAutoSync` ruft `enable()`/`disable()`; `main()` re-registriert bei Start, wenn Pref an). Constraints: `NetworkType.connected` = **beliebiges Netz inkl. mobiler Daten** (bewusst nicht nur WLAN), `ExistingPeriodicWorkPolicy.keep`, `initialDelay` 15 min. **Kein Custom-Application-Setup nötig** – workmanager 0.9.x registriert sich über `androidx.startup`; Permissions (INTERNET/ACCESS_NETWORK_STATE/WAKE_LOCK/RECEIVE_BOOT_COMPLETED) werden automatisch gemergt. Android-Minimum für Periodic ist 15 min; 1 h ist akkuschonend (~0,3–1 %/Tag), reale Intervalle dehnt Doze. Nur Android (iOS/Desktop = no-op).
