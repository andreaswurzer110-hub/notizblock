## Was das ist

Plattformübergreifende Notizblock-App in **Flutter (Dart)**.
Eine Codebasis für **Android, Windows und Linux**.

Kernfunktionen:
- Reine Text-Notizen (kein Markdown, keine Bilder, keine Checklisten)
- Post-it-Style Widgets: auf Android Homescreen-Widgets, auf Windows „Sticky Notes"-Fenster
- Schlichtes Design, abgerundete Ecken
- Mehrsprachig, **Deutsch als Standard**, Sprache umschaltbar
- Google-Drive-Backup/Sync für plattformübergreifenden Abgleich

## Tech-Stack

- **State:** provider
- **Lokale DB:** sqflite (+ sqflite_common_ffi für Windows/Linux), path, path_provider
- **Google Drive:** googleapis, googleapis_auth, google_sign_in, http
- **Widgets (Android):** home_widget
- **Desktop-Fenster:** window_manager (Position/Größe der Sticky-Notes), url_launcher (OAuth-Browser)
- **UI:** flutter_staggered_grid_view, Material Design
- **Sonstiges:** uuid, intl, shared_preferences, flutter_localizations

## Architektur

```
lib/
  models/      # Note-Datenklasse
  providers/   # State (provider)
  screens/     # Bildschirme/Seiten
  widgets/     # wiederverwendbare UI-Komponenten
  services/    # database_service.dart, google_drive_service.dart, …
  l10n/        # Lokalisierung (de = Standard)
```

**Note-Model:** id (uuid), title, content, createdAt, modifiedAt, color (Default `#FFFDE7`), isPinned, isArchived.
**DatabaseService:** Singleton; auf Windows/Linux `sqfliteFfiInit()` + `databaseFactoryFfi`; Tabelle `notes` mit Indizes auf `modifiedAt` und `isPinned`. DB-Version aktuell 2 (`deletions`-Tabelle) → Schema-Änderungen über `_onUpgrade` migrieren, nicht hart neu anlegen. **DB-Speicherort:** Desktop (Windows/Linux) = `getApplicationSupportDirectory()` (`%APPDATA%\com.example\notizblock\` bzw. `~/.local/share/…`, neben `sticky_state/`); Android/iOS = `getApplicationDocumentsDirectory()` (dort liest das Home-Widget `notes.json`). Früher lag die DB auf Desktop im Dokumente-Ordner → einmalige Migration via `_migrateDbFromDocuments` (kopiert DB + WAL/SHM/Journal, falls am neuen Ort noch keine existiert).

## Bekannte Stolpersteine / offene Punkte

- **home_widget:** mind. `^0.7.0` – ältere Versionen ziehen das gelöschte Android-**v1-Embedding** und der Build scheitert. Bei „deleted Android v1 embedding"-Fehler zuerst hier ansetzen.
- **sqlite3.dll auf Windows/Linux:** `sqflite_common_ffi` lädt die native `sqlite3`-Lib zur Laufzeit, bündelt sie aber nicht selbst. Ohne `sqlite3_flutter_libs` als Dependency wirft `openDatabase()` „Failed to load dynamic library 'sqlite3.dll'" → quasi die ganze Desktop-App tot. `sqlite3_flutter_libs` ist daher Pflicht (steht in `pubspec.yaml`).
- **Windows-Build braucht VS-C++-Workload:** `flutter doctor` muss „Desktop development with C++" grün zeigen (MSVC, C++ CMake tools, Windows SDK). Fehlt die Workload → „Unable to find suitable Visual Studio toolchain". Im Visual-Studio-Installer nachinstallieren.
- **Linux (Zorin OS):** Plattform via `flutter create --platforms=linux .` ergänzt (`linux/`-Runner, Binary `notizblock`, App-ID `at.aw.notizblock`). **Build nur auf Linux-Host** (nicht von Windows aus cross-baubar). Build-Deps auf Zorin/Ubuntu: `clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev libstdc++-12-dev`. Bauen + installieren über `scripts/install_linux.sh` (legt Bundle nach `~/.local/opt/notizblock`, Icon nach hicolor, `.desktop`-Launcher). Plattform-Anpassungen: Autostart = `.desktop` in `~/.config/autostart/` (`AutostartService`, Linux-Zweig); Sticky-Prozess-Check via `/proc/<pid>` + Schließen via `kill` (statt `tasklist`/`taskkill`); UI-Gates auf `_isDesktop` statt `Platform.isWindows`. Fenster-Icon: `gtk_window_set_icon_name(window,"notizblock")` in `my_application.cc` → löst sich nach Icon-Install auf. **Wayland-Caveat:** absolute Fensterposition (`window_manager` setPosition/getBounds für Sticky-Bounds + `--pos`) funktioniert nur unter **X11** zuverlässig; unter Wayland ignoriert der Compositor App-Positionen → ggf. Xorg-Session wählen. **Sticky-Bounds speichern (alle Desktops, v.a. Linux):** Die Fenster-Lage wird NICHT nur über die `window_manager`-Events (`onWindowMoved/Resized/Close`) gesichert – die feuern auf Linux unzuverlässig, und beim Reboot wird der Sticky-Prozess hart beendet (kein sauberes Close) → letzte Größe ginge verloren. Deshalb pollt `StickyNoteScreen._boundsSaveTimer` alle 2 s `getBounds()` und schreibt bei Änderung (`_saveBounds` mit Diff-Check). Unter **nativem** Wayland bleibt die **Position** verloren (`gtk_window_get_position`→0,0, `gtk_window_move` ignoriert). **Lösung: der Linux-Runner (`linux/runner/main.cc`) erzwingt standardmäßig `setenv("GDK_BACKEND","x11",0)`** → die App läuft über **XWayland**, dort funktionieren get/setPosition wieder, also merkt sie sich Position+Größe auch in einer Wayland-Sitzung (wie Windows). Gilt für jeden Prozess (Haupt+Stickys, gleiche Binary), überschreibbar mit `GDK_BACKEND=wayland ./notizblock`. Trade-off XWayland: fraktionale Skalierung evtl. leicht unscharf. (Reine Wayland-Sessions ohne XWayland gibt's auf GNOME praktisch nicht.) Eine echte Xorg-Sitzung tut dasselbe ganz ohne den Trick. **Taskleisten-Gruppierung:** Die `.desktop`-Datei MUSS nach der GTK `application-id` (`at.aw.notizblock`) benannt sein (`at.aw.notizblock.desktop`), NICHT `notizblock.desktop`. Jedes Fenster (Hauptfenster + Sticky-Prozesse) trägt `_GTK_APPLICATION_ID=at.aw.notizblock`; GNOME/Zorin sucht dazu die gleichnamige `.desktop` und gruppiert alle Fenster unter EINEM Taskleisten-Eintrag. Bei Namens-Mismatch findet GNOME keine Zuordnung → jedes Fenster wird einzeln angezeigt (war real ein Bug). `StartupWMClass=at.aw.notizblock` zusätzlich als X11-Fallback. Fix sitzt in `scripts/install_linux.sh`.
- **google_sign_in hat keine Desktop-Impl:** `signInSilently()`/`signIn()` daher nur auf Android/iOS aufrufen (in `main.dart` per `Platform.is…` gekapselt), sonst Exception beim Start.
- **WICHTIG – Android-Access-Token lebt nur ~1 h (Auth-Header NIE einfrieren):** `GoogleAuthClient` muss die Header **pro Request** frisch aus `_googleSignIn.currentUser?.authHeaders` holen, NICHT einmal beim Login einen Header-Schnappschuss speichern. Sonst liefert der erste Drive-Request nach ~1 h **401** → `_handleAuthFailure()` loggt hart aus → Status springt auf „abgemeldet" (durchgestrichenes `sync_disabled`-Icon). War real ein Bug: Nutzer wurde am Handy nach ~1 h Vordergrund-Nutzung und „fast bei jedem Netzwechsel" ausgeloggt (Netzwechsel = nur der Auslöser, weil resume einen Sync feuert; das abgelaufene Token war die Ursache). Erst durch den sichtbaren Login-Status (v1.20.0) aufgefallen, vorher heilte der nächste App-Start still. **Hat NICHTS mit dem OAuth-Consent-Screen „Testing→Produktion" zu tun** – das betrifft nur das Desktop-7-Tage-**Refresh**-Token, nicht das Android-1-h-**Access**-Token. Fix: (1) Header pro Request frisch; (2) bei 401 mobil `clearAuthCache()` + Token still erneuern und Operation **einmal** neu versuchen (`_refreshMobileToken` + `allowAuthRetry`-Param in `_doSynchronize`/`createBackup`/`restoreBackup`), erst bei erneutem Fehlschlag echtes `_handleAuthFailure`; (3) Sicherheitsnetz in `NotesProvider._runAutoSync`: bei `!isSignedIn` vor dem Sync still `signInSilently()`. Desktop unberührt (`autoRefreshingClient` refresht selbst; dortiges 401/invalid_grant = totes Refresh-Token = echtes Neu-Anmelden nötig).

Mobil (Android/iOS) nutzt weiter `google_sign_in`. Desktop-`client_id`/`client_secret` (Typ „Desktop app") stehen in `lib/services/google_drive_config.dart` (enthält echte Secrets → bei Git unbedingt gitignoren). Cloud-Projekt-ID `445597891658`, Drive API aktiviert, Test-User eingetragen. Sync = last-write-wins über `modifiedAt` (so gewollt). **Offen für Android:** OAuth-Client Typ „Android" mit Paketname + SHA-1 in der Cloud Console anlegen, dann auf echtem Gerät testen.

Layout `note_widget.xml`: Content-`maxLines` hoch (1000) → zeigt beim Vergrößern mehr. Notizfarbe wird im Provider auf den Hintergrund übernommen (API≥31 `setBackgroundTintList` → Ecken bleiben rund, sonst `setBackgroundColor`), Textfarbe nach Luminanz. **WICHTIG:** Update-Broadcast muss voll qualifiziert sein (`qualifiedAndroidName='com.example.notizblock.NoteWidgetProvider'` in `WidgetService.updateWidget`), weil die Provider-Klasse im Namespace `com.example.notizblock` liegt, die applicationId aber `at.aw.notizblock` ist – sonst trifft der Refresh die Klasse nicht. **WICHTIG – Broadcast zentral in `_updateWidgetJsonFile`:** Nach dem Schreiben von `notes.json` ruft `DatabaseService._updateWidgetJsonFile` direkt `WidgetService.instance.updateWidget()` auf. Das ist der gemeinsame Chokepoint ALLER DB-Schreibwege (auch Delta-Sync/`insertOrUpdateNotes`). Vorher feuerte der Broadcast nur über `NotesProvider` bei lokalen Aktionen → Remote-Sync-Änderungen aktualisierten das Widget erst nach dem 1-h-`updatePeriodMillis`. Den Broadcast also NICHT aus `_updateWidgetJsonFile` entfernen.
- **Editor speichert beim Tippen (entprellt 1 s) bei bestehenden Notizen** (`_saveDebounce` in `NoteEditorScreen`), damit der Auto-Sync zeitnah hochlädt statt erst beim Schließen. Neue Notizen weiterhin erst beim Schließen (sonst Duplikate, da `widget.note` null bleibt). Lifecycle: Sync auch bei `paused` (App geht in den Hintergrund) – nicht nur `resumed` –, damit Änderungen vor dem Einfrieren der Timer noch hochgehen.
- **Cross-Device-Pull (alle Plattformen):** `NotesProvider._remotePullTimer` zieht alle 15 s von Drive (`_runAutoSync`). Läuft nur im Vordergrund – auf Android pausieren Timer im Hintergrund (kein Akkuverbrauch). Zusätzlich: einmaliger Sync ~2 s nach Start **und** Sofort-Sync bei Rückkehr in den Vordergrund (`WidgetsBindingObserver.didChangeAppLifecycleState` → resumed). Alles nur bei aktivem Auto-Sync + Anmeldung. So fließt es in beide Richtungen (PC↔Handy).
- **Hintergrund-Sync Android (`workmanager`, `BackgroundSyncService`):** Da Vordergrund-Timer im Hintergrund pausieren, zieht zusätzlich ein **WorkManager-Periodic-Job** alle **1 h** auch bei geschlossener App von Drive – so aktualisiert sich das Homescreen-Widget mit Fremdgeräte-Änderungen ohne App-Öffnen. Top-Level `backgroundSyncCallbackDispatcher` (`@pragma('vm:entry-point')`, eigenes Isolate): `ensureInitialized` → Auto-Sync-Pref prüfen → `signInSilently()` → `synchronize()`; der Widget-Broadcast läuft dann über `DatabaseService._updateWidgetJsonFile`. Job-Lifecycle an den Auto-Sync-Schalter gekoppelt (`SettingsProvider.setAutoSync` ruft `enable()`/`disable()`; `main()` re-registriert bei Start, wenn Pref an). Constraints: `NetworkType.connected` = **beliebiges Netz inkl. mobiler Daten** (bewusst nicht nur WLAN), `ExistingPeriodicWorkPolicy.keep`, `initialDelay` 15 min. **Kein Custom-Application-Setup nötig** – workmanager 0.9.x registriert sich über `androidx.startup`; Permissions (INTERNET/ACCESS_NETWORK_STATE/WAKE_LOCK/RECEIVE_BOOT_COMPLETED) werden automatisch gemergt. Android-Minimum für Periodic ist 15 min; 1 h ist akkuschonend (~0,3–1 %/Tag), reale Intervalle dehnt Doze. Nur Android (iOS/Desktop = no-op).
- **Sticky-Fenster syncen selbst (Windows):** Jedes Sticky-Fenster synct automatisch – nach Änderung (entprellt 2 s) + periodischer Pull (15 s), gegated über den Auto-Sync-Schalter (`_runStickyAutoSync` in `StickyNoteScreen`). Der kleine Sync-Button unten rechts (`_syncNow`) ist nur Absicherung. Dafür meldet sich der Sticky-Prozess in `main()` per `signInSilently` an. Mehrere Prozesse syncen ggf. gleichzeitig → `synchronize()` macht `prefs.reload()` für prozessübergreifend frische Zeitstempel.
- **Android-Widget-Navigation & Buttons:** Widget-Tap → `_openNoteEditor` öffnet den Editor via `pushAndRemoveUntil` als EINZIGEN Screen → einmal Zurück führt zum Homescreen (`SystemNavigator.pop` wenn `!canPop`). `NoteEditorScreen.openedFromWidget` zeigt dann oben einen Home-Button (`_goToMainMenu` → `HomeScreen` als neue Wurzel). Das Android-Homescreen-Widget hat zusätzlich ein ☰-Symbol (`widget_menu`), das die App via `ACTION_MAIN`+`CLEAR_TASK` frisch in der Hauptansicht öffnet. Editor hat außerdem einen manuellen Sync-Button (Absicherung).
- **Android-Widget „Jetzt synchronisieren" (Zeit = Button):** Die Zeit-Anzeige im Homescreen-Widget (`widget_time`, gerahmt via `drawable/widget_sync_button.xml`) ist zugleich ein Sync-Button – Platz oben ist auf der kleinsten Widget-Stufe knapp, daher Doppelnutzung. Klick → **Hintergrund-Sync ohne App-Öffnen** über `home_widget`: `NoteWidgetProvider` setzt auf `widget_time` ein `HomeWidgetBackgroundIntent.getBroadcast(context, notizblock://sync_now)`; der Dart-`widgetBackgroundCallback` (`@pragma('vm:entry-point')`, eigenes Isolate) fängt `host=='sync_now'` ab → `signInSilently()` → `synchronize()` → `updateWidget()`. Bewusst NICHT an den Auto-Sync-Schalter gekoppelt (explizite Nutzeraktion). **WICHTIG – Manifest:** `home_widget` liefert `HomeWidgetBackgroundReceiver` + `HomeWidgetBackgroundService` (JobIntentService), deklariert sie aber NICHT selbst → beide müssen in `android/app/src/main/AndroidManifest.xml` stehen (Receiver mit `action es.antonborri.home_widget.action.BACKGROUND`, Service mit `permission BIND_JOB_SERVICE`), sonst passiert beim Klick nichts. Der Callback-Handle wird beim App-Start via `WidgetService.initialize()` (`registerInteractivityCallback`) persistiert → funktioniert auch bei geschlossener App. Desktop-Pendant: im Sticky-Fenster und im Editor ist die Zeit-Anzeige ebenfalls tappbar (löst `_syncNow` aus, gleiche Funktion wie der Sync-Button; im Editor nur bei angemeldetem Drive).
- **Auto-Sync:** Schalter „Automatisch synchronisieren". `NotesProvider._scheduleAutoSync()` löst nach jeder Datenänderung einen **entprellten** Sync aus (2 s nach der letzten Änderung), wenn angemeldet + Schalter an – **auf allen Plattformen** (Android lädt dank Delta nur die geänderte Notiz hoch). Nur das Fremdänderungs-Polling (`_externalChangeTimer`, 0,8 s) bleibt **Desktop-exklusiv**.
- **Delta-Sync / Drive-Layout (seit Umstieg von Single-File):** Im Ordner „Notizblock Backup": `notes/<id>.json` (aktueller Stand je Notiz, inkl. archivierte mit `isArchived`-Flag), `tombstones/<id>.json` (`{id, deletedAt}` für Löschungen), `history/<id>__<ts>__<titel>.json` (Versions-Snapshots). `notizblock_backup.json` bleibt als Voll-Backup-Fallback (nur von „Backup erstellen" geschrieben, NICHT vom Delta-Sync). `synchronize()` in `google_drive_service.dart`: Pull nur Dateien mit `modifiedTime > lastRemoteSync` (Drive-Zeit, in prefs `last_remote_sync_time`), Push nur lokal seit `last_sync_timestamp` geänderte Notizen + offene Tombstones (DB-Tabelle `deletions`, via `_afterLocalWrite`/`getPendingDeletions`). Last-write-wins über `modifiedAt` vs. `deletedAt`. Reentrancy: `synchronize()` hält den laufenden Sync als `_inFlight`-Future; ein paralleler Aufruf (z.B. Button während Auto-Sync) bekommt denselben Future zurück (kein „läuft bereits"-Fehler mehr). Eigentliche Logik in `_doSynchronize()`. Historie: pro Notiz neueste **30** behalten; gelöschte Notizen (Tombstone + Historie) nach **30 Tagen** entsorgt (`_pruneHistory`, läuft nur wenn etwas synchronisiert wurde). Einmalige Migration vom alten Gesamt-Backup über `_migrateLegacyIfNeeded` (prefs `delta_migrated`), respektiert `modifiedAt` (überschreibt neuere lokale Notizen nicht). DB-Version **2** (`deletions`-Tabelle, `_onUpgrade`). Löschungen propagieren jetzt korrekt (vorher Bug: gelöschte Notizen kamen via Big-File zurück).
- **Prozessübergreifende Aktualisierung (Desktop):** Sticky-Note-Fenster sind eigene Prozesse und schreiben direkt in die DB. Die Hauptapp pollt deshalb alle 1,5 s `DatabaseService.getLastModified()` (mtime von `.db`/`-wal`/`-journal`/`-shm`). Bei Fremdänderung: stilles Neuladen der Liste **und** Auto-Sync zu Drive. So ist die Hauptapp die einzige Sync-Instanz (keine konkurrierenden Uploads aus mehreren Prozessen). `_lastDbMtime` wird nach eigenen Schreibvorgängen via `_afterLocalWrite()` gesetzt, damit der eigene Write nicht als Fremdänderung gilt. Voraussetzung fürs Sync von Widget-Edits: Hauptprozess läuft (tut er normal, beim Autostart minimiert).
- **Live-Editor (`NoteEditorScreen`):** hört auf `NotesProvider` und übernimmt externe Änderungen an der offenen Notiz live in Titel/Inhalt – aber nur, wenn das jeweilige Feld **nicht fokussiert** ist (`FocusNode.hasFocus`), damit aktuelles Tippen nie überschrieben wird. So ziehen mehrere offene Fenster derselben Notiz nach.
- **Sticky-Fenster live (`StickyNoteScreen`):** eigener Prozess → pollt selbst alle 1 s `getNoteById` und übernimmt externe Änderungen (Inhalt nur wenn Feld nicht fokussiert; Farbe/Titel immer). Extern gelöschte Notiz → Fenster schließt sich. Nötig, weil ein Sticky-Fenster sonst seinen Stand vom Öffnungszeitpunkt behält.
- **WICHTIG – `modifiedAt` nie ohne echte Änderung bumpen:** `Note.copyWith` setzt `modifiedAt = now`. Auto-Sync-Pfade dürfen `_saveNote` daher NUR aufrufen, wenn sich Titel/Inhalt wirklich geändert haben (Sticky `_saveNote` vergleicht vorher; Editor speichert beim Sync nur bei `_hasChanges`; externe Übernahmen setzen via `_applyingExternal` kein `_hasChanges`). Sonst bumpte jedes offene Fenster alle 30 s den Zeitstempel auf „jetzt" → Anzeige zeigt immer die aktuelle Zeit UND das Fenster gewann fälschlich last-write-wins → Änderungen anderer Geräte gingen verloren. (War real ein Bug.)
- **Änderungszeit-Anzeige:** Notizkarte (Liste) zeigt `modifiedAt`; Windows-Sticky unten links (`DateFormat('d.M. HH:mm')`); Android-Widget rechts vom Titel (`widget_time`, Provider `formatTime` per Substring, kein java.time wegen Desugaring).
- **WICHTIG – `last_sync_timestamp`-Watermark = Sync-START, nicht Sync-Ende:** `_doSynchronize()` hält das neue lokale Watermark **vor** dem Erfassen der geänderten Notizen fest (`localSyncStart = DateTime.now()`) und schreibt am Ende genau diesen Wert – NICHT `DateTime.now()` am Ende. Sonst: eine Notiz, die WÄHREND eines laufenden Syncs gespeichert wird (z.B. weiter getippt, nachdem ihr alter Stand schon gepusht war), hat ein `modifiedAt` < End-`now()` → der nächste `getNotesModifiedAfter()`-Lauf überspringt sie → sie wird NIE hochgeladen. War real ein Bug: nur Zwischenstand „Test m" landete in Drive, finaler Stand „Test machen" wurde verschluckt. Trat fast nur am Handy auf (Tippen mit Pausen ⇒ ständig Save-(1 s)+Auto-Sync-(2 s)-Zyklen mitten im Editieren + Sync bei `paused`; langsameres Mobilnetz = breiteres Race-Fenster). Watermark also NICHT wieder auf End-`now()` ändern.
- **Sync-Konflikt = last-write-wins über `modifiedAt` (Gerät-Uhr!).** Bei Uhren-Differenz zwischen Geräten kann theoretisch die „falsche" Version gewinnen. **Safety-Net:** jede gepushte Version liegt vorher als Snapshot in `history/`, also nichts ist je wirklich verloren – im Zweifel von dort wiederherstellen. `synchronize()` überspringt beim Push IDs, die im selben Lauf gerade per Pull übernommen wurden (`appliedIds`) → verhindert Ping-Pong/Zurückschreiben.
- **Drive-Setup-Stolpersteine (real aufgetreten):** „403 access_denied" = Test-User fehlt im OAuth-Consent-Screen. „403 Drive API has not been used/disabled" = Drive API im richtigen Projekt aktivieren (leicht im falschen Projekt zu aktivieren!). Beides reine Cloud-Config, kein Code.
- **Windows-Widgets / Sticky Notes:** Umgesetzt über **separate Prozesse** (`Process.start … --sticky-note <id>`), NICHT `desktop_multi_window`. Jeder Prozess steuert sein Fenster via `window_manager`. „Widget"-Status (welche Notizen beim Start aufgehen) = `ids`-Liste in eigener Datei `<AppSupport>/sticky_state/widget_ids.json` (`StickyNoteService.getWidgetNoteIds`/`setWidget`), pro Notiz per Rechtsklick-Kontextmenü umschaltbar. **WICHTIG – NICHT in shared_preferences:** Lag früher dort mit der falschen Annahme „schreibt nur die Hauptapp → unkritisch". Real schreiben aber auch die Sticky-Prozesse in dieselbe prefs-Datei (beim Sync `last_sync_timestamp` etc.); da prefs immer die GANZE Datei schreibt, kippte ein Sticky-Prozess mit veraltetem Snapshot die Anheft-Änderungen der Hauptapp zurück → gelöste Widgets kamen wieder, neu angeheftete verschwanden nach dem Neustart (war real ein Bug; Workaround war: einstellen, alle Sticky-Tasks beenden, neu starten). Eigene Datei = nur die Hauptapp schreibt → behoben.
